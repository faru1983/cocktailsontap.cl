# 🧠 AI Context & Development Guidelines - Cocktails on Tap

Este archivo es la "Memoria del Proyecto" para asistentes de IA. Contiene las reglas críticas de negocio, arquitectura y decisiones técnicas para asegurar que cada nueva modificación respete la visión del proyecto.

---

## 🛠️ Reglas de Oro del Desarrollo (MANDATORIAS)

1.  **Tailwind CSS First**: Está terminantemente prohibido crear archivos `.css` adicionales o usar etiquetas `<style>`. Se debe usar **Tailwind CSS v4** de forma exclusiva para todo el styling.
2.  **Separación de Responsabilidades**: 
    - Lógica de negocio pura en `lib/wizardLogic.ts`.
    - Acciones de servidor en `app/actions/`.
    - Componentes atómicos en `components/ui/`.
3.  **Seguridad de Datos**: Nunca hardcodear URLs o llaves API. Usar siempre `process.env` o las constantes configuradas en `lib/config.ts`.
4.  **Tipado Estricto**: Todo componente o función nueva debe estar debidamente tipado con TypeScript en `lib/types.ts`.
5.  **Preservar Tests**: Cualquier cambio en la lógica de precios o litros debe ser validado ejecutando `node --env-file=.env.local tests/test-calculations.js`.
6.  **Auto-Documentación (CRÍTICO)**: Al realizar cambios importantes en la arquitectura, lógica de negocio o integraciones, la IA **DEBE** actualizar automáticamente este archivo (`.ai-context.md`) **Y** el `README.md` simultáneamente para asegurar que la documentación externa e interna refleje el estado real del proyecto.
7.  **Manejo Naive de Fechas**: Para integraciones con Make/Google Calendar, las fechas/horas enviadas vía Webhook **DEBEN** ser "Naive Strings" (formato `YYYY-MM-DDTHH:mm:ss` generado vía `formatLiteral`). NUNCA enviar con sufijos de zona horaria (Z) ni objetos Date de JS directamente al Webhook, para evitar que Vercel (UTC) desplace la hora local de Chile.

## 📐 Arquitectura de Integraciones

### 1. Make.com (Automatización Logística)
El sistema envía un webhook a Make en `confirmQuote.ts` que dispara dos procesos:
- **Evento de Servicio**: Basado en `start_date` e `isoStart`.
- **Evento de Retiro**: Basado en `pickup_start` y `pickup_end`. 
- **Lógica de Títulos**: 
  - Servicio: `Cócteles - [Nombre] [Invitados]px`
  - Retiro: `Retiro - [Nombre] [Apellido]`

### 2. Resend (Comunicaciones)
Las plantillas están centralizadas en `lib/emails.ts`. 
- **Remitente**: `contacto@cocktailsontap.cl`.
- **Diseño**: Mobile-first, colores de marca (`#E2A049`), botones de acción destacados.
- **Flujo**: Se envían 4 correos (Cliente/Admin al crear, Cliente/Admin al confirmar).

### 3. Supabase (Capa de Persistencia)
- **Clients (CRM)**: Tabla central con `email` (Unique), `first_name`, `last_name` y `phone`. Se usa un sistema de **Upsert** por email para evitar duplicados y centralizar el historial.
- **Quotes**: Tabla principal. Vinculada a `clients` vía `client_id`. Mantiene una copia (snapshot) de los datos del cliente en el momento de la cotización por razones históricas.
- **Quote_Items**: Relación 1:N que guarda los productos seleccionados y su precio congelado.

## 📋 Lógica de Negocio Crítica

### Sistema de Barriles (Dispensing)
- **Muro de Coctelería**: Solo aparece si `total_liters >= 30` y los productos son de tamaño `10L`, `20L` o `30L`.
- **Costo Instalación**: El Muro tiene un costo base (`MURO_INSTALLATION_COST`) definido en `lib/config.ts`.
- **Cálculo de Litros**: Lógica basada en (invitados * tragos_por_persona * 0.25).

### Estados de Cotización
- `draft`: Cotización inicial creada (sin datos de contacto completos).
- `confirmed`: El cliente ha presionado "Confirmar Reserva" (se activa Make y se envían correos de abono).

## 🚀 Guía de Mantenimiento

- **Actualizar Precios**: Modificar los registros en la tabla `products` de Supabase. El sistema es reactivo a la DB.
- **Agregar Comunas**: Modificar la tabla `comunas` en Supabase.
- **Probar Emails**: `npx tsx --tsconfig tsconfig.json --env-file=.env.local tests/test-email-preview.ts`.

### 🎯 Mejoras Recientes (Marzo 2026)
- **Validación Robusta**: Se implementó `Zod` para validar todas las Server Actions (`CreateQuoteSchema`, `ConfirmQuoteSchema`).
- **Configuración Centralizada**: Todas las constantes críticas (emails, costos, whatsapp) ahora residen exclusivamente en `lib/config.ts`.
- **Seguridad Senior**: El recalculo de totales y costos de instalación se realiza ahora en el lado del servidor durante la confirmación, ignorando valores manipulables desde el cliente.
- **Fix de Fechas (Make)**: Se mantiene el envío de fechas como "Naive Strings" (`formatLiteral`) para asegurar que la hora ingresada por el cliente (ej: 15:00) sea la misma que aparezca en Google Calendar, independientemente de la zona horaria del servidor.
- **Recálculo de Seguridad**: Todos los totales, envíos e instalaciones se validan en el servidor durante la confirmación para evitar manipulaciones de precio desde el cliente.
